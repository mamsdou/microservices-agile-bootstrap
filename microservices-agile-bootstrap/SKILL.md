# Microservices + agile documentation: bootstrap

This skill produces a coherent repository in one pass: **runnable code**, **infrastructure** (Docker, Kubernetes, ELK, Kafka, PostgreSQL) and **Scrum documentation** adapted to the user's business domain. The technical part is generated by a deterministic script (`scripts/scaffold.py`) so the skeleton is always the same; the product part (vision, backlog, sprints) is written by you, because it depends on the domain.

Stack generated by the script (if the user wants something else, tell them what will need manual changes): Java 21, Maven multi-module, Spring Boot 3.3 + Spring Cloud 2023.0 (Config Server, Eureka, Gateway), Angular 15, Kafka (KRaft), PostgreSQL 16 (one database per service), ELK 8 (Logstash TCP), Docker Compose, Kubernetes (kustomize), Keycloak authentication (OIDC/JWT, per-service roles). Documentation in English.

## Workflow

### 1. Gather the parameters (ask few questions)

You need: a **project name** (kebab-case, e.g. `shopflow`), a one-sentence **business domain**, a Java **groupId** (default `com.example.<project>`), the list of **business microservices** (default: 2) and the domain's **user roles** (e.g. customer, courier, merchant, administrator; default `admin,user`). For each service, work out who can write and who can only read (`:w=role+role:r=role`); without this the first role writes and the others read, which is rarely right. If the user does not specify the domain, suggest a plausible one and continue. Derive the services from the domain (e.g. e-commerce → `catalog`, `order`, `notification`); the first publishes Kafka events and the others consume them, so choose an order that makes business sense.

Output folder: if the session has no project folder, generate in the current directory under `<project-name>/`.

### 2. Generate the technical skeleton

```bash
python <skill>/scripts/scaffold.py --project shopflow --title "ShopFlow" \
  --domain "E-commerce platform" --group-id com.acme.shopflow \
  --roles admin,merchant,customer \
  --services "catalog:8081:w=admin+merchant:r=customer,order:8082:w=customer+admin:r=merchant,notification:8083:w=admin" \
  --out ./shopflow
```

What is produced: parent POM + `config-server`, `discovery-server`, `api-gateway`, one module per business service (REST API, JPA/Flyway, Kafka publishing after commit, Kafka consumption, JSON logs to Logstash, unit test), Angular 15 `frontend/` (+ nginx, OIDC login), Keycloak (imported realm `infra/keycloak/realm.json` with one dev account per role; gateway and services validate the JWT and apply the roles from `config-repo/<service>.yml`; 401/403 tests per service), `docker-compose.yml`, `k8s/` (kustomize), GitHub Actions CI, `Makefile`, and `docs/architecture/` + `docs/adr/` + `docs/agile/` + `docs/quality/` already filled in with the real ports, topics and services. Read `references/architecture.md` if you need to modify or extend the skeleton (add a service, change a version, understand a choice).

The script refuses to overwrite a non-empty folder unless `--force` is passed. Use `--force` only when the user asks for it.

### 3. Write the Scrum product documents

The script deliberately does not write them: they must speak the language of the user's business. Read `references/agile-docs.md` (expected structure of each document, INVEST user story examples with Gherkin criteria), then write in `docs/product/` and `docs/sprints/`:

- `vision.md` — product vision, personas, measurable goals, scope / out of scope
- `roadmap.md` — releases and milestones (MoSCoW prioritization)
- `product-backlog.md` — epics → user stories (value, acceptance criteria, estimate, priority), including technical enablement stories
- `sprint-0.md` — "foundations": what the generated skeleton already covers (checked) and what remains
- `sprint-1-planning.md` — sprint goal and realistic sprint backlog
- `risks.md` — risk and dependency register

Each story must stand on its own: "As a… I want… so that…", verifiable acceptance criteria, size. Link stories to the skeleton's services (one service = one data owner), otherwise the backlog and the architecture diverge from week 1.

Update `docs/README.md` (index) to link these new documents, and complete the "Context" section of the root `README.md` with a 3-line vision.

### 4. Check before handing back

- `docker compose config -q` in the generated folder (validates YAML and variables)
- `kubectl kustomize k8s` or `kubectl apply -k k8s --dry-run=client` if `kubectl` is available
- `mvn -B verify` if Maven is available. The project targets Java 21; with a local JDK 17, add `-Djava.version=17` (the code uses no Java 21 API) to check compilation and unit tests, and state clearly that compilation under Java 21 was not run
- `npm install && npx ng build --configuration production` in `frontend/` if Node is available
- review the tree: no leftover `@@…@@` or `__…__` token (`grep -r "@@" .`)

Report honestly what was checked and what was not (e.g. Java 21 compilation, full stack startup).

### 5. Summarize for the user

Give the tree in a few lines, the startup commands (`docker compose up -d --build`, URLs: frontend :4200, gateway :8080, Eureka :8761, Kibana :5601, Kafka UI :8090) and the 3 natural next steps (start Sprint 1, restrict data access by owner, implement the Outbox pattern). Point out that the Keycloak login flow is only verified by unit tests and a gateway test until the Docker stack has been run. The full Compose stack needs about 6–8 GB of RAM: warn the user.

## Principles

- **One database per service**, never cross-service joins: this is what makes services truly independent, and the backlog must reflect that boundary.
- **No real secrets** in the repository: default values are dev values, flagged as such; production goes through Kubernetes secrets or a vault.
- **Decisions are recorded as ADRs** (`docs/adr/`). If the user changes a choice (e.g. Gradle, Keycloak), add an ADR that supersedes the old one rather than rewriting history.
- **Increment = value**: Sprint 0 must not last more than one sprint; the skeleton exists so that Sprint 1 delivers a first vertical slice (front → gateway → service → database → Kafka).
